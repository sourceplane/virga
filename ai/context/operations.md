# virga — operating contract (for humans and agents)

This is the standing guide to how this site is deployed and operated.
Instance facts (live URLs, workspace, secrets inventory) live in
[deployment.md](deployment.md), regenerated by `flows/phases/08-docs`; this
file is the contract that stays true between deployments. It is written to
give an agent with repository read access enough context to reason about and
operate the system without any other source.

## What this system is

A single-owner website on Cloudflare alone, expressed as an Orun
component-native desired-state repo. Cloudflare is the only provider in the
loop: Workers for compute, D1 for the database, KV for the edge rate
limiter, Email Service for delivery.

- **`apps/site-api`** — the only publicly routable Worker. Visitor write
  paths (subscribe, confirm, unsubscribe, form submissions, reactions,
  views), public reads (reaction and view counts, launch rankings), and the
  owner routes under `/v1/owner/` behind a bearer token. Bindings: `SITE_DB`
  (D1), `RATE_LIMIT_KV` (KV), `MAIL_WORKER` (service).
- **`apps/mail-worker`** — internal (no workers.dev route), reached only
  through site-api's service binding. Renders the four templates, sends
  through `local-debug` or Cloudflare Email Service, and runs newsletter
  broadcasts resumably against the deliveries table.
- **`apps/web-site`** — the public site, Next.js on Workers + Static Assets.
  Content is Markdown in `content/`; every content route is prerendered at
  build. The client islands call site-api from the browser.
- **`infra/terraform/*`** — the data plane: the D1 database and the
  rate-limiter KV namespace per environment, plus the (parked) custom-domain
  root. **`infra/db-migrate`** — migrations over D1's REST API (plan on PRs,
  apply on merge).
- **`packages/*`** — the contracts, the D1 seam and repositories, shared
  helpers, the owner CLI.

Environments: **`stage`** and **`prod`** are fully provisioned and deployed;
**`dev` is verify-only by design** — lanes run, nothing deploys.

## There is no console

The owner operates from two places and no others:

1. **git** — content, configuration and code. A merge to `main` converges.
2. **the `virga` CLI** — `health`, `stats`, `subscribers list|export`,
   `submissions list|mark`, `issues list|show|create|send`. It needs
   `VIRGA_API_URL` and `VIRGA_OWNER_TOKEN` and speaks only `/v1/owner/*`.

If an operation is not in that list, it does not exist yet — do not invent an
admin endpoint.

## Identity and tenancy

Every remote operation runs against ONE Orun workspace. This repo DECLARES
its tenancy in `intent.yaml` (`execution.state.workspace`) — committed,
enforced, and what CI uses. Do not remove that line; headless credentials
depend on it.

## Deploying

CI is Orun: `.github/workflows/ci.yml` calls only `orun plan` and `orun run`.
On a pull request every changed component runs its verify lane; on a merge to
`main` the deploy lanes converge stage, then prod.

`ci.yml` is gated behind the `ORUN_CI` repository variable. Until a product is
bootstrapped, `verify.yml` (install → wire fixtures → typecheck → lint → test
→ build → checksum check) is the merge gate and needs nothing but the repo.

## Secrets

| Secret | Where | Without it |
|---|---|---|
| `OWNER_TOKEN` | site-api | owner routes answer 503 |
| `TOKEN_SECRET` | site-api **and** mail-worker (same value) | unsubscribe answers 503; broadcasts carry no unsubscribe link |
| `FINGERPRINT_SALT` | site-api | fingerprints still work, but do not rotate daily |
| `TURNSTILE_SECRET` | site-api (optional) | no challenge on subscribe and forms |

Provider credentials are never stored: they are brokered per run from the
workspace's Cloudflare connection. Terraform outputs travel as
lease-published `WIRING_*` secrets and are rendered into Worker configs at
deploy time, so no resource id is ever committed.

## Data plane facts worth knowing before you touch it

- **D1 has no interactive transactions.** `executor.transaction(...)` runs
  its statements in order with NO rollback. Where all-or-nothing matters, use
  one statement with `RETURNING`, or an `ON CONFLICT` upsert — the broadcast
  enqueue is written as a single `INSERT … SELECT` for exactly this reason.
- **SQLite types.** Timestamps are ISO-8601 text, JSON documents are text,
  booleans are 0/1. `@site/db/json` owns the decoding.
- **No schemas.** Bounded contexts are table-name prefixes (`audience_`,
  `forms_`, `engagement_`, `newsletter_`) enforced in the repositories.
- **Migrations are checksummed.** Editing an applied migration is what the
  guard exists to stop; add a new one instead.

## Runbook

| Situation | Do |
|---|---|
| A visitor reports a broken subscribe | `virga health`, then check the site-api logs for `rate_limit.backend_failure` or `mail.call_failed`. A mail failure never fails a subscribe: the row is `pending` and the next subscribe re-sends. |
| A broadcast stopped part-way | `virga issues show <id>` — the delivery counts say what remains. Re-run `virga issues send <id> --yes`; only rows still `queued` are attempted. |
| Spam through a form | `virga submissions mark <id> spam`. If it is sustained, set `TURNSTILE_SECRET` and redeploy. |
| A deploy failed | Re-run the convergence (`flows/common/converge.sh <run-id>`); it is a true resume. |
| The site is fine but counts look frozen | The rate limiter fails OPEN, so counts keep working during a KV outage; check `x-ratelimit-*` headers are present on a write. |
